## 3. 결과를 증명하는 방법

### 3.1 회고 검증 (핵심 결과)

> **CVE-2024-0037 패치(2024-02)로 만든 규칙을 그 시점 코드에 돌렸을 때, 이후 따로 고쳐진 곳을 미리 찾았는가.**

| 이후 고쳐진 곳 | CVE | 추가된 검사 |
| --- | --- | --- |
| PrintManagerService | CVE-2024-0053 (2024-03) | `validateIconUserBoundary` |
| SettingsLib EditUserPhotoController | CVE-2024-43082 (2024-11) | `getUserIdFromUri(pictureUri)` 와 `myUserId` 비교 |
| ChooserActivity | CVE-2025-22416 (2025-04) | `checkGrantUriPermission` |

정답을 우리가 아니라 **구글의 이후 패치**가 정하므로 자기 채점이 아니다. 한 곳이라도 맞히면 "공개 패치에서 아직 안 고쳐진 변종을 찾을 수 있다"는 근거가 된다. 회고 검증 주 결과는 LLM 을 끄고 낸다 (LLM 이 이후 패치를 학습했을 수 있음, [limitations.md](limitations.md) L3).

### 3.2 Vanir 비교 지표 (초안, 팀 확정 필요)

Vanir 는 Google 의 **패치 누락 탐지 도구**다. "같은 코드에 이 패치가 적용됐나"를 본다. 우리는 "**다른 코드에 같은 실수가 남았나**"를 본다. 그래서 순위를 겨루기보다 **서로 무엇을 잡는지**를 같은 입력으로 비교한다.

| 지표 | 계산 | 기대 |
| --- | --- | --- |
| 원본 위치 탐지 | 패치 전 코드에서 원래 고친 위치를 잡는가 | 둘 다 잡아야 함 |
| **Vanir 가 놓친 정탐 수** | 우리 후보 중 사람 라벨 `tp` 이면서 Vanir 결과에 없는 것 | 우리 강점 |
| 회고 검증 적중 | §3.1 의 3곳 중 미리 찾은 수 | 우리 강점 (Vanir 는 다른 코드는 대상 아님) |
| 처리 가능 패치 비율 | 보안 공지 패치 중 규칙(또는 시그니처)을 만들 수 있었던 비율 | 유형별로 비교 |
| Precision@N | 상위 N 후보 중 `tp` 비율, 2인 독립 라벨 + κ | 우리 약점일 수 있음, 솔직히 보고 |
| 처리 시간 | CVE 1건당 전체 소요 | 참고 |

### 3.3 독립 정답으로 채점

- 새 CVE 의 정답은 **추출기를 만들지 않은 사람**이 쓴다 (현재 A 수동 분류 vs 분류기 일치 9/14).
- 시험용 CVE 는 미리 떼어 두고, 도구를 다 만들 때까지 보지 않는다.

## 4. 기여와 차용을 구분해서 말하기

### 4.1 Source-Guard-Sink 의 출처

"Source-Guard-Sink(S·G·S)"는 **우리 팀이 붙인 이름**이고 개념은 기존 연구에서 왔다. **Vanir 에서 온 것이 아니다** (11/26 면담 답변 정정).

- **Source → Sink:** 정적 분석(taint 분석)의 기본 틀. 믿을 수 없는 입력이 위험한 동작까지 흐르는지 본다.
- **가운데 Guard:** 안드로이드 접근 통제 연구들.

| 연구 | 한 줄 요약 | 우리가 가져온 것 |
| --- | --- | --- |
| Kratos (NDSS 2016) | 같은 동작으로 가는 여러 경로 중 검사가 빠진 경로를 찾음 | "한 곳엔 검사가 있고 다른 곳엔 없다" → 변종 찾기 |
| AceDroid (NDSS 2018) | 제각각인 검사(UID·권한·사용자 제한)를 유형으로 묶어 비교 | Guard 유형 정규화 (Guard 사전) |
| Invetter (CCS 2018) | 입력값 검사도 보안 검사로 봄 | `PRECONDITION_ADDITION` |
| ACMiner | 시스템 서비스의 권한 확인 코드를 모아 평가 | Guard 수집 |
| Axplorer (USENIX Security 2016) | 검사가 위험 동작과 떨어진 상위 호출자에 있는 경우가 많음 | 경로 전체에서 Guard 찾기 |

발표 문구 예: "Kratos·AceDroid 등 안드로이드 접근 통제 연구의 '입력 → 검사 → 민감 동작' 분석 방식을 따른다 (우리는 S·G·S 라 부른다)."

S·G·S 는 주력 유형(`GUARD_ADDITION`)의 규칙·검증·후보 판정을 정하는 뼈대다. 다른 두 유형은 각각 Precondition-Target API, Unsafe API-Safe API 로 표현한다.

### 4.2 우리 기여라고 말할 부분

- **공개 패치 하나에서 "어떤 검사가 필요한지"를 자동으로 뽑아** 탐지 규칙으로 만든다.
- 그 규칙을 **패치 전·후 코드로 검증**(전 탐지·후 미탐지·대조군 예산)해 통과한 것만 쓴다.
- 패치 유형별로 다른 규칙 템플릿(`perm_guard`·`api_guard`·`api_usage`)을 쓰고, 맞지 않는 패치는 사유와 함께 걸러낸다.

## 5. 정직하게 말할 한계

숨기지 않고 수치와 함께 보고서 "한계" 항목에 둔다 ([limitations.md](limitations.md)).

- 결과는 **정적 분석 후보**다. 동적 재현은 후속 범위라 실제 악용 가능성은 사람 라벨로만 판단한다.
- Tree-sitter 는 타입 정보가 없어 호출 대상을 이름으로 근사한다. 해석 못 한 경로는 `unknown` 으로 표시하고 비율을 보고한다.
- 기준선이 2건으로 적다. 회고 검증과 독립 라벨로 보완한다.
- 실제로 남아 있는 변종이 0건일 수 있다. 그 경우에도 회고 검증 결과와 유형별 커버리지로 도구의 동작을 보여준다.
