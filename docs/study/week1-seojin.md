# 안드로이드 프레임워크 취약점 분석을 위한 개념 정리

## 1. 계층 구조와 시스템 서버의 위치

### 안드로이드

- 리눅스 커널 위에 여러 층을 쌓아 만든 시스템

#### 구조

```
┌────────────────────────────────────────────────────────┐
│ System Apps  (Launcher, Settings, SystemUI, Phone ...) │  ← 일부는 platform 서명/priv-app
├────────────────────────────────────────────────────────┤
│ Java API Framework                                     │  ★ 우리 타깃 (앱 프로세스 쪽)
│  Activity/Package/Window/Clipboard...Manager, View,    │
│  Content Providers, Resource Manager                   │
├──────────────────────────┬─────────────────────────────┤
│ Native C/C++ Libraries   │ Android Runtime (ART)       │
│  libc, SQLite, OpenGL,   │  dex→oat/AOT+JIT, GC,       │
│  Media, Webkit           │  core libs, zygote          │
├──────────────────────────┴─────────────────────────────┤
│ HAL  (audio, camera, sensors, bluetooth ...)           │  ← Treble 이후 별도 프로세스/AIDL HAL
├────────────────────────────────────────────────────────┤
│ Linux Kernel                                           │
│  드라이버, 전원관리, ★Binder(IPC) 드라이버,            │
│  DAC(UID/GID), SELinux(MAC), seccomp                   │
└────────────────────────────────────────────────────────┘
```

- 우리가 쓰는 앱들
- 자바로 작성된 프레임워크
- 네이티브 라이브러리와 자바 런타임(ART)
- 하드웨어 추상화 계층(HAL)
- 커널

### 프레임워크

1. 앱 프로세스 안에 링크되어 실행되는 코드
    - ActivityManager, PackageManager 같은 매니저 클래스들이 여기 속한다.
2. 다른 하나는 system_server라는 별도의 프로세스 안에서 도는 실제 구현부 
    - 앱이 매니저 클래스의 메서드를 부르면 그 호출은 프로세스 경계를 넘어 system_server로 전달되고, 진짜 동작은 거기서 일어남
        - 앱은 자기 프로세스 안에서 무슨 짓을 해도 자기 것만 망가뜨릴 수 있다. 의미 있는 권한 상승은 system_server가 앱 대신 무언가를 해줄 때만 가능하다.
        - 즉 우리가 찾는 취약점은 거의 전부 이 두 프로세스 사이의 경계에 있다.

#### 부팅 순서

```
Bootloader → Linux Kernel → init (init.rc 파싱)
   ├── servicemanager        (Binder 서비스 이름 등록소, uid=system)
   ├── zygote (app_process)  (프레임워크 프리로드, fork 모체)
   │     └── fork → system_server   ★ uid=1000(system), 거의 모든 시스템 서비스가 여기 산다
   │     └── fork → 모든 앱 프로세스  ★ uid=10000+
   ├── surfaceflinger, media, vold, installd ...
   └── SystemServer → ActivityManagerService.systemReady() → Launcher 실행
```

- 커널이 올라오면 init이 시작되고, init이 servicemanager와 zygote를 띄운다.
- zygote는 프레임워크 클래스를 미리 메모리에 올려둔 상태로 대기하다가, 필요할 때 자기 자신을 복제해서 앱 프로세스를 만든다.
    - 앱 시작이 빠른 것도, 모든 앱이 같은 초기 상태를 갖는 것도 이 때문이다. -
- system_server 역시 zygote가 복제해서 만든 자식이다. 다만 이 자식만은 시스템 권한을 유지한 채 살아남아, 수십 개의 시스템 서비스를 품고 기기가 꺼질 때까지 돈다.
- zygote가 모든 앱의 부모라는 사실은 그 자체로 공격 표면이다.
    - zygote가 앱을 만들 때 쓰는 명령 채널에 이상한 값을 흘려넣을 수 있다면 임의의 앱으로 변신할 수 있다는 뜻

## 2. 앱이라는 실행 단위

### 앱

- APK 파일로 배포
    - 그 안에는 코드와 리소스, 그리고 AndroidManifest.xml이 들어 있음
    - 분석 관점에서는 매니페스트가 중요
        - 이 앱이 어떤 권한을 요구하는지, 어떤 컴포넌트를 외부에 열어두었는지가 전부 여기 적혀 있기 때문이다.

#### 앱 컴포넌트 4종류

| 컴포넌트 | 역할 | 공격 면 |
| --- | --- | --- |
| **Activity** | 화면 | exported activity로 임의 화면 실행, Intent redirection 종착지 |
| **Service** | 백그라운드 작업 | bind/start 시 권한 검사 누락 |
| **BroadcastReceiver** | 이벤트 수신 | protected broadcast 사칭, sticky/ordered 악용 |
| **ContentProvider** | 데이터 공유 | SQL injection, **path traversal**, URI permission 오용 |

각 컴포넌트

- 외부에 공개 or 앱 내부에서만 쓰일 수도 있음
- 이 공개 여부가 곧 공격 가능 여부를 결정

### Intent

: 컴포넌트 사이를 오가는 메시지

1. 명시적 인텐트: 받는 쪽을 직접 지정 
2. 암시적 인텐트: 어떤 동작을 하고 싶다는 설명만 담아 시스템이 수신자를 고르게 함
    - 암시적 인텐트는 편하지만 누가 받을지 실행 시점에 결정되기 때문에, 엉뚱한 앱이 가로채거나 중간에 방향이 틀어질 수 있다.
    - 인텐트 안에는 다른 인텐트나 임의의 객체를 실어 보낼 수도 있다.

#### 버전별 제약 강화

| 버전 (targetSdk) | 변화 |
| --- | --- |
| 12 (31) | `intent-filter` 있는 컴포넌트는 **`android:exported` 명시 필수**, `PendingIntent`는 **mutability 플래그 필수**(`FLAG_IMMUTABLE`/`FLAG_MUTABLE`) |
| 13 (33) | 런타임 알림 권한, 일부 암시적 브로드캐스트 제한 |
| 14 (34) | **Safer Intents**: 암시적 Intent는 exported 컴포넌트에만 배달, 등록 시 `RECEIVER_EXPORTED/NOT_EXPORTED` 명시 필수 |
| 15~16 (35~) | 백그라운드 액티비티 실행 제한 강화 등 |

## 3. AOSP 소스를 읽는 방법

소스를 전부 내려받을 필요는 없다. cs.android.com에서 검색하고 읽는 편이 훨씬 빠르고, 브랜치를 바꿔가며 버전별 코드를 비교할 수도 있다.

#### 기억해야 할 디렉토리

- frameworks/base/core/java 아래: 앱 프로세스에 링크되는 코드
    - 매니저 클래스들, Binder와 Parcel, Intent가 전부 여기 있음
- frameworks/base/services/core/java 아래: system_server가 실제로 실행하는 서비스 구현
    - 액티비티 관리, 패키지 관리, 윈도우 관리 같은 것들이 하위 디렉토리로 나뉘어 있음

#### API → 실제로 무슨 일을 하는지 따라가는 순서

1.  매니저 클래스를 찾음
    - 그 안에는 반드시 원격 인터페이스를 가리키는 필드가 있고, 매니저의 메서드는 대개 그 인터페이스로 호출을 넘기는 한두 줄에 불과
2. 그 인터페이스의 AIDL 파일을 본다. 
    - 여기서 어떤 인자들이 프로세스 경계를 넘어가는지가 드러난다.
3. 마지막으로 그 인터페이스의 Stub을 상속한 클래스를 검색하면 system_server 안의 진짜 구현이 나온다. 
    - 권한 검사는 거의 언제나 그 구현 메서드의 첫머리에 있다.

#### 패치를 찾는 경로

1. 매달 발표되는 안드로이드 보안 공지에 CVE 목록이 있고, 프레임워크 섹션의 각 항목에는 AOSP 커밋 링크가 달려 있다. 
2. 그 링크를 따라가면 곧바로 diff를 볼 수 있다. 
3. 다만 공지에 링크가 없는 항목도 있다. 구글 플레이 시스템 업데이트로만 배포되거나 파트너 전용으로 처리된 경우인데, 이런 것들은 우리가 재현할 방법이 없으니 후보에서 빼는 게 맞다. 
    - 버그 추적기의 상세 내용 역시 대부분 비공개라서, 사실상 공지 한 줄과 커밋 하나가 우리가 가진 정보의 전부임.
    - 그 두 가지만으로 원인을 복원하는 것이 이 작업의 본질인 것!!

## 4. UID가 곧 보안 경계다

#### 안드로이드

- 앱 하나 = 리눅스 사용자 하나로 취급
- 앱을 설치 ⇒ 고유한 UID가 부여되고, 그 앱의 모든 프로세스와 파일이 그 UID를 갖는다.
    - 서로 다른 앱은 서로 다른 사용자이므로, 리눅스가 원래부터 갖고 있던 파일 권한 체계만으로도 앱끼리 격리된다.

#### UID 구역

| 범위 | 이름 | 예 |
| --- | --- | --- |
| 0 | `AID_ROOT` | init, (userdebug의 adbd) |
| 1000 | `AID_SYSTEM` | **system_server**, 대부분의 시스템 서비스 |
| 1001~ | 고정 AID | `AID_RADIO`(1001), `AID_BLUETOOTH`, `AID_SHELL`(2000, adb shell) … |
| 10000~19999 | 일반 앱 (`AID_APP_START`) | 설치 순서대로 부여 |
| 99000~99999 | isolated 프로세스 | WebView 렌더러 등, 권한 거의 0 |

#### 멀티 유저 UID

```c
uid = userId * 100000 + appId        (PER_USER_RANGE = 100000)
예) appId 10123, 두 번째 프로필(userId=10) → 1010123
UserHandle.getUserId(uid) = uid / 100000
UserHandle.getAppId(uid)  = uid % 100000
```

if) 기기에 프로필이 여러 개 있으면, 같은 앱이라도 프로필마다 다른 UID를 갖는다. 

- 실제 UID는 프로필 번호에 십만을 곱하고 앱 고유 번호를 더한 값이다. 그래서 어떤 UID를 받았을 때, 십만으로 나누면 프로필 번호가 나오고 나머지가 앱 번호가 된다.
    - 이 구조를 알아두어야 하는 이유는, 시스템 서비스가 앱 번호만 비교하고 프로필 번호를 확인하지 않는 실수 많음….
    - 그러면 한 프로필의 앱이 다른 프로필의 데이터를 읽는 일이 생긴다. 실제 CVE로 반복해서 등장하는 유형이니까 주의!!!

## 5. 샌드박스를 지탱하는 세 겹

### 앱 격리

1. DAC (Discretionary Access Control) — 커널의 전통적 UID/파일 퍼미션
    - `/data/data/<pkg>` 는 그 앱 UID 소유, 모드 `700` (Android 6.0부터 751→700 강화)
    - 다른 앱의 데이터에 접근 = `EACCES`
        
        root나 시스템 권한을 얻으면 전부 무력화되고, 무엇이 허용되는지가 코드 여기저기에 흩어진다.
        
2. MAC (SELinux) — Android 5.0부터 전면 enforcing
    - 프로세스는 도메인(`untrusted_app`, `priv_app`, `platform_app`, `system_server`, `zygote`…)을 갖고,
    파일/소켓/서비스는 타입 레이블을 갖는다. 커널이 중앙 정책으로 허용된 조합만 통과시킨다.
    - Android 9부터 targetSdk≥28인 앱은 앱별 개별 SELinux 샌드박스.
    - root라도 도메인 밖은 못 나간다 → DAC를 뚫어도 MAC이 남는다. (이중 방어)
    - Binder 서비스도 정책 대상: `allow untrusted_app clipboard_service:service_manager find;` 같은 규칙이 없으면 서비스 핸들 자체를 못 얻는다.
        
        일반 앱은 untrusted_app 도메인에서 돌고, system_server는 자기 이름의 도메인에서 돈다. 이 방식의 핵심은 root조차 자기 도메인에 허용되지 않은 일은 못 한다는 점이다. 파일 권한을 뚫어도 정책이 막으면 소용이 없다. 안드로이드 9부터는 앱마다 개별 샌드박스를 갖도록 세분화되었다.
        
3. seccomp-bpf (Android 8~): 앱이 호출 가능한 syscall 축소.

```bash
adb shell ps -AZ | grep -E "system_server|u0_a"    # 컨텍스트(도메인) 확인
# 예) u:r:system_server:s0   system_server
#     u:r:untrusted_app:s0:c123,c256,c512,c768   com.example
adb logcat | grep -i avc          # SELinux 차단 로그 (denied)

```

⇒ 분석할 때 이 세 겹을 구분하는 것이 실질적으로 중요!!

if) PoC가 실패했을 때 프레임워크의 권한 검사에 걸린 것인지, 파일 권한에 걸린 것인지, SELinux 정책에 걸린 것인지에 따라 다음에 할 일이 완전히 달라지기 때문

## 6. 권한 모델과 두 종류의 검사

### 앱

- 매니페스트에 필요한 권한을 선언하고, 권한마다 보호 수준이 정해져 있음
    
    
    | 레벨 | 부여 방식 | 비고 |
    | --- | --- | --- |
    | `normal` | 설치 시 자동 | 위험 낮음 |
    | `dangerous` | **런타임 사용자 동의** | Android 6.0+ |
    | `signature` | **같은 서명키**일 때만 | 플랫폼 키 = 사실상 시스템 전용 |
    | `signature|privileged` | priv-app(`/system/priv-app`) + `privapp-permissions.xml` 허용 목록 | 벤더 앱 |
    | appop / special | 설정 화면에서 별도 승인 | `SYSTEM_ALERT_WINDOW`, `MANAGE_EXTERNAL_STORAGE` 등 |
- 위험도가 낮은 것: 설치와 동시에 부여되고, 개인정보에 관련된 것은 사용자가 실행 중에 승인해야 한다.
- 특별히 민감한 것들: 같은 키로 서명된 앱에만 주어지는데, 플랫폼 키로 서명된 앱이란 사실상 시스템 자신뿐이므로 일반 앱은 아무리 선언해도 얻을 수 없다.
    - 여기에 더해 앱 작업이라 불리는 별도의 게이트가 있어서, 권한을 가졌더라도 사용자가 설정에서 꺼둘 수 있다.
    

#### 검사가 이루어지는 위치가 두 군데라는 것이 중요!!

1. 선언적 검사
    - 컴포넌트에 권한을 명시해두면 시스템이 그 컴포넌트에 접근하려는 쪽의 권한을 대신 확인해줌. 편하지만 진입 경로 하나만 보호
2. 명령적 검사
    - 서비스 구현 메서드 안에서 직접 호출자의 권한을 확인하는 코드를 쓰는 것이다.
        - 프레임워크 취약점의 대다수가 바로 이 지점에서 생김!!
        - 새 메서드를 추가하면서 검사를 빠뜨리거나, 여러 진입 경로 중 일부에만 검사를 넣거나, 내부용으로 만든 메서드가 어느 순간 외부에서 도달 가능해지는 식임

#### 보안 경계 정리

| 경계 | 무엇이 막는가 | 뚫리면 |
| --- | --- | --- |
| 앱 ↔︎ 앱 | UID + SELinux 앱별 카테고리 | 타 앱 데이터 탈취 |
| 앱 ↔︎ system_server | **Binder 권한/신원 검사** | ★ EoP (system 권한 획득) |
| 앱 ↔︎ 커널 | seccomp + SELinux | 커널 취약점(범위 밖) |
| 사용자 프로필 간 | userId 검사 | cross-user 정보 노출 |
| 일반앱 ↔︎ priv-app | 서명/priv 권한 | 특권 앱 사칭 |
| 앱 ↔︎ zygote | 소켓 접근 제어 + 인자 검증 | 전 앱 장악 (CVE-2024-31317) |

## 7. Binder, 경계를 넘는 유일한 통로

### Binder

- 앱과 system_server는 서로 다른 UID를 가진 별개의 프로세스
- 그 사이를 잇는 것이 Binder
    - 소켓이나 파이프 대신 Binder를 쓰는 이유는 몇 가지가 있음
    - 보안 관점에서 결정적인 것은 커널이 송신자의 신원을 보증한다는 점
    - 앱이 호출을 보내면 커널의 Binder 드라이버가 그 트랜잭션에 송신자의 실제 UID와 PID를 직접 기록 ← 앱이 이 값을 위조할 방법은 없음
    

#### 호출이 오가는 모습

- 앱 쪽에는 프록시 객체가 있고 서버 쪽에는 스텁이 있음
- 앱이 매니저 메서드를 부르면 프록시가 인자들을 Parcel이라는 버퍼에 차례로 써넣고, 메서드를 식별하는 번호와 함께 커널로 넘긴다. 커널은 그것을 상대 프로세스로 전달하고, 스텁이 같은 순서로 읽어서 진짜 구현 메서드를 호출한다.
    - AIDL 인터페이스의 인자로 넘어오는 값은 전부 앱이 마음대로 채운 값
        - 호출자의 패키지 이름, 대상 사용자 번호, 심지어 UID를 인자로 받는 인터페이스도 있는데, 이 값들은 어떤 의미에서도 신뢰할 수 없음
        - 앱은 다른 앱의 패키지 이름을 적어 보낼 수 있고, 남의 프로필 번호를 적어 보낼 수 있다. 신뢰할 수 있는 것은 오직 커널이 채워준 호출자 UID뿐이다.

#### Parcel 관련 보안

- 쓴 순서와 타입 그대로 읽어야 한다는 규칙이다.
- if) 어긋나면 남은 바이트가 다음 객체로 해석된다.
    - 앱이 넘긴 데이터 묶음을 system_server가 읽었다가 다시 써서 다른 곳으로 전달하는 경우가 흔한데, 그 안에 쓰기 길이와 읽기 길이가 다른 객체가 하나 섞여 있으면 시스템 쪽에서 공격자가 의도한 전혀 다른 객체가 튀어나오게 된다.

#### 호출 방식

- 동기 or 비동기
    - 비동기 호출: 응답을 기다리지 않기 때문에 서버 쪽에서 예외가 나도 호출한 앱은 그 사실을 알 수 없다. 재현 성공 여부를 앱의 반환값으로만 판단하면 놓치게 되고, 로그를 봐야 한다.

## 8. 호출자 신원을 다루는 방식과 그 함정

### System Service

- 호출자가 누구인지 알아야 일을 할 수 있다.
- Binder는 현재 처리 중인 호출의 UID와 PID를 알려주는 방법을 제공
    - 이 값은 커널이 보증하므로 위조할 수 없음 but, 이 편리한 장치에 몇 가지 함정이 있음
    1. 같은 프로세스 안에서 직접 호출하면 호출자 UID는 자기 자신의 UID가 된다
        - system_server 내부의 다른 코드가 이 메서드를 부르면 호출자는 시스템이 된다는 뜻이다. 외부에서 들어오는 경로를 막아도 내부를 경유하는 우회로가 열려 있으면 검사가 무의미해진다.
    2. (중요) 신원을 일시적으로 지우는 기능
        - 시스템 서비스는 앱을 대신해서 특권 작업을 해야 할 때가 있다. 그럴 때 호출자 신원을 잠시 치워두고 자기 자신, 즉 시스템의 권한으로 동작한 다음 원래대로 되돌린다.
            
            ```java

            try {
                // 이 구간에서는 호출자가 앱이 아니라 시스템으로 간주된다
                doPrivilegedWork();
            } finally {
                Binder.restoreCallingIdentity(token);
            }
            ```
            
    
    문제??
    
    - 이 구간이 필요 이상으로 넓어질 때 생김
    - 신원을 지운 상태에서 권한 검사를 하면 시스템 자신을 검사하는 꼴이 되어 언제나 통과
    - 특히 호출자 또는 자기 자신 중 하나라도 권한이 있으면 허용하는 형태의 검사 함수를 이 구간 안에서 쓰면 사실상 검사가 사라짐

    1. PID로 권한을 판단하면 안 된다.

    - 먼저 커널이 보증한 호출자 UID를 가져오고, 앱이 보낸 패키지 이름이 그 UID의 것이 맞는지 확인하고, 앱이 지정한 사용자 프로필이 접근해도 되는 범위인지 확인하고, 필요한 권한을 가졌는지 확인한다.정말 특권이 필요한 최소 구간에서만 신원을 지운다.

## 9. system_server의 구조적 성질

### system_server가 하나의 프로세스

1. 공유 상태
    - 그 안의 어떤 서비스를 뚫든 결과는 똑같이 시스템 권한이다. 클립보드 서비스의 사소한 버그와 패키지 관리자의 버그가 최종적으로 같은 수준의 권한을 준다.
2. 단일 실패 지점
    - 그 안의 어떤 서비스가 죽든 프로세스 전체가 죽는다.
    - system_server에서 처리되지 않은 예외가 발생하면 프로세스가 종료되고 init이 zygote부터 다시 시작한다. 사용자 입장에서는 기기가 재부팅되는 것처럼 보인다.
3. 워치독
    - 주요 스레드가 일정 시간 안에 응답하지 않으면 워치독이 system_server를 강제로 종료한다.
    - 교착, 무한루프 유발 취약점

#### Verifier Agent가 잡아야할 로그 신호

| 신호 | logcat 패턴(예) | 의미 |
| --- | --- | --- |

| PoC 자체 결과 | `POC_RESULT=VULNERABLE|PATCHED` | 우리가 정한 계약 |

## 10. 취약점이 생기는 자리

#### 프레임워크 취약점의 유형

1. 권한 검사 누락
    - Binder로 노출된 메서드에 권한 확인이 아예 없거나, 여러 진입 경로 중 일부에만 있다. 패치는 보통 검사 한 덩어리를 추가하는 것으로 끝나고, 재현과 판정이 가장 깔끔
2. 신원 혼동 
    - 신원을 지운 구간이 너무 넓거나, 그 안에서 자기 자신을 허용하는 형태의 검사를 쓴 경우다. 패치를 보면 검사가 신원을 지우기 전으로 옮겨가거나, 지우는 구간이 눈에 띄게 좁아진다.
3. 혼란한 대리인으로 불림
    - 권한 있는 컴포넌트가 앱이 건네준 인텐트를 검증 없이 대신 실행해주거나, 앱이 만든 보류 인텐트를 그대로 발송해주는 경우다. 실행되는 것은 앱의 의도인데 신원과 권한은 시스템의 것이 된다. 인텐트 리다이렉션이라는 이름으로도 부르며, 안드로이드에서 가장 자주 반복되는 설계상의 실수다.
4. 직렬화 불일치
    - Parcel 문제
5. 입력 검증 부족
    - 길이나 개수, 범위를 확인하지 않고 앱이 준 값을 시스템 자료구조에 그대로 넣어서 시스템 프로세스를 죽이는 유형이다. 설정 데이터베이스처럼 재부팅 후에도 남는 곳에 저장되면 기기를 못 쓰게 만들 수도 있음
6. 경로 조작
    - 파일 이름이나 URI에 상위 디렉토리 참조가 섞여 들어가는데 정규화를 하지 않는 경우다. 패치는 정규화한 경로가 허용된 디렉토리 안에 있는지 확인하는 코드로 나타난다.
7. 사용자 프로필 경계 누락
8. 패키지 이름 사칭
    - 둘 다 앞에서 설명한 원리, 즉 앱이 보낸 인자를 그대로 믿었다는 하나의 원인에서 나옴
9. 불완전한 패치

## 11. 정리

앱은 자기 UID에 갇혀 있고, 커널의 파일 권한과 SELinux가 그 경계를 지킨다. 앱이 그 경계 너머의 기능을 쓰는 유일한 합법적 방법은 Binder를 통해 system_server에게 부탁하는 것이다. 커널이 부탁한 자의 신원은 보증해주지만, 부탁에 함께 실려오는 나머지 값들은 전부 앱이 지어낸 것이다. 그래서 system_server의 각 메서드는 스스로 호출자를 확인하고, 그가 지목한 대상이 정당한지 확인하고, 권한을 확인한 다음에야 일을 해야 한다.

프레임워크 1-day란 이 확인 절차 중 하나가 빠졌거나 잘못된 자리에 놓여 있던 흔적이고, 패치란 그 절차를 제자리에 돌려놓은 기록이다. 우리가 diff에서 읽어내야 하는 것 ⇒ 이 코드는 무엇을 확인하기 시작했는지를 보는 것
